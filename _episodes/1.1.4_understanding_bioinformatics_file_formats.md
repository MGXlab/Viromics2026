## Exercise 1 — name that format

Below are short, anonymised snippets. For each one, identify the file format and name one specific clue in the snippet that gave it away (a symbol, a line count, a keyword, a column pattern).

> Exercise 1
>
> Snippet A
> ```text
> contig_1 length=4521
> ATGCGTACGTTAGCATGCTAGCATGCATCGATCGTAGCTAGCATCGATCG
> ```
> 
> Snippet B
> ```text
> @read_001
> ATGCGTACGTTAGCATGCTAGC
> +
> IIIIIIIIIIIIIIIIIIIIII
> ```
> 
> Snippet C
> ```text
> contig_1  Prodigal  CDS  50  409  .  +  0  ID=gene_1;product=hypothetical protein
> ```
> 
> {: .source}
{: .challenge}


> Solution
> A: FASTA. Starts with > followed by a header, then one or more lines of raw sequence.
> B: FASTQ. Exactly 4 lines per record: @ identifier, sequence, + separator, quality string of the same length.
> C: GFF/GTF. Tab-separated, 9 columns, describing a genomic feature (here a coding sequence, CDS) with a start and end coordinate.
> {: .source}
{: .solution}

Exercise 2 — spot what's broken
Exercise 2

Here is a FASTQ record someone sent you, claiming their pipeline is failing on it:

@read_042
ATGCGTACGTTAGCATGCTAGCATG
+
IIIIIIIIIIIIIIIII
What's wrong with this record?
Why would this cause a downstream tool (e.g. a quality-checking program) to fail or produce nonsense results?
Solution

The sequence line has 25 characters, but the quality line only has 18 — they must always be the same length, since each quality character corresponds to exactly one base. A file with mismatched lengths like this is corrupted, and most tools will either crash outright or silently misinterpret which quality score belongs to which base — a good example of why a quick sanity check with wc -l/head on new data is worth doing before trusting it.

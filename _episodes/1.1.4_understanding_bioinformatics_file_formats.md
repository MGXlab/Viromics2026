> ## Exercise 1 - Name that format
>
> Below are short, anonymised snippets. For each one, identify the file format and name one specific clue in the snippet that gave it away (a symbol, a line count, a keyword, a column pattern).
> 
> Snippet A
> ```text
> contig_1 length=4521
> ATGCGTACGTTAGCATGCTAGCATGCATCGATCGTAGCTAGCATCGATCG
> ```
> 
> Snippet B
> ```text
> @read_001
> ATGCGTACGTTAGCATGCTAGC
> +
> IIIIIIIIIIIIIIIIIIIIII
> ```
> 
> Snippet C
> ```text
> contig_1  Prodigal  CDS  50  409  .  +  0  ID=gene_1;product=hypothetical protein
> ```
> 
> {: .source}
{: .challenge}


> ## Solution:
> A: FASTA. Starts with > followed by a header, then one or more lines of raw sequence.
> B: FASTQ. Exactly 4 lines per record: @ identifier, sequence, + separator, quality string of the same length.
> C: GFF/GTF. Tab-separated, 9 columns, describing a genomic feature (here a coding sequence, CDS) with a start and end coordinate.
> 
> {: .source}
{: .solution}

> ## Bonus Exercise: — spot what's broken
>
> ```text
> Here is a FASTQ record someone sent you, claiming their pipeline is failing on it:
> @read_042
> ATGCGTACGTTAGCATGCTAGCATG
> +
> IIIIIIIIIIIIIIIII
> ```
> 
> What's wrong with this record?
> Why would this cause a downstream tool (e.g. a quality-checking program) to fail or produce nonsense results?
>
> {: .source}
{: .challenge}

> ## Solution:
>
> The sequence line has 25 characters, but the quality line only has 18 — they must always be the same length, since each quality character corresponds to exactly one base. A file with mismatched lengths like this is corrupted, and most tools will either crash outright or silently misinterpret which quality score belongs to which base — a good example of why a quick sanity check with wc -l/head on new data is worth doing before trusting it.
>
> {: .source}
{: .solution}


## Video 2: FASTA, FASTQ, and metadata in more depth

Video 2 (11 min) covers sequence file types in more depth: FASTA, FASTQ, quality scores, metadata (TSV) files, and compressed files.

[![Basic file formats in bioinformatics](https://img.youtube.com/vi/D4WDdAbZW1Y/0.jpg)]( https://www.youtube.com/watch?v=D4WDdAbZW1Y&ab_channel=BasE.Dutilh)

> ## Discuss
> With a neighbour: a FASTQ file has 4 lines per read. What does each of those 4 lines represent, and why is it useful to have a quality value per base rather than just one overall score for the whole read?
> {: .source}
{: .challenge}

> ## Solution:
> @ + sequence identifier
> the raw nucleotide sequence
> a + separator line (optionally repeating the identifier)
> a string of characters encoding quality, one per base in line 2
>
> A per-base score matters because quality often varies along a single read (commonly dropping towards the ends) — a single overall score would hide that and make it impossible to trim just the low-quality parts of an otherwise good read. We'll come back to exactly how those quality characters are decoded into a number when we look at real quality scores this afternoon.
> 
> {: .source}
{: .solution}



## Viewing file contents in the terminal

Terminal Basics covered navigating the filesystem and combining commands with pipes (`|`) and `>`. Now let's add a few commands specifically for looking *inside* files. You'll use these constantly for the rest of the course.

```bash
cat file.txt      # print the whole file to the screen
head file.txt     # print the first 10 lines
tail file.txt     # print the last 10 lines
less file.txt     # open the file for scrolling — press q to quit
```

> ## Exercise — try it on a real file
>
> You should already have sequence_file_count.txt in your workspace from the Terminal Basics lesson.
>
> 1. `cat sequence_file_count.txt` — see the whole thing.
> 2. `head -1 sequence_file_count.txt` — just the first line.
> {: .source}
{: .challenge}

> ## Solution:
> Since this file only has one line, `cat` and `head -1` show the same thing here. The difference matters much more once files get longer, which is exactly the case for our sequencing data next.
> 
> {: .source}
{: .solution}

Your sequencing files are gzip-compressed, so `cat/head/less` won't show anything readable if you use them directly. You need to decompress on the fly instead:

```bash
zcat file.fastq.gz | head -10
zcat file.fastq.gz | tail -10
zless file.fastq.gz    # scroll with arrow keys, quit with q
```

You'll also sometimes want to search inside a file for lines matching a pattern — `grep` does this for plain text, and `zgrep` does the same for gzipped files:

```bash
grep "search_term" file.txt
zgrep "search_term" file.fastq.gz
zgrep -c "search_term" file.fastq.gz    # -c counts matching lines instead of printing them
```

> 1. `sample_metadata.tsv` (a small plain-text table, a few KB)

{: .solution}

## Now let's look at your own data

You've just practiced recognising formats in isolation. Let's apply the same eye to the real sequencing data in your workspace.

> ## Exercise 4
>
> Choose the virome.fastq.gz file in your data/sequences/ folder and answer:
> 1. How many lines does this file have?
> 2. How many sequences (reads) are present in the file? (Hint: how many lines correspond to one read?)
> 3. Print the first 5 lines and the last 5 lines in the terminal.
> 4. What differences do you observe between these lines (identifier line vs. sequence line vs. + line vs. quality line)?
>
> {: .source}
{: .challenge}

> ## Solution
> Total lines ÷ 4 = number of reads, since every FASTQ record spans exactly 4 lines.
> The identifier line starts with `@`, the sequence line is made of `A/C/G/T/N` characters, the third line starts with `+`, and the quality line is the same length as the sequence line but made of a wider range of ASCII characters.
> {: .source}
{: .solution}

> ## Exercise 5 — counting things
>
> Using `grep/zgrep`, `wc -l`, and what you know about FASTQ structure:
> Count how many read identifier lines (`@...`) appear in `virome.fastq.gz`. Does it match the read count you calculated in Exercise 4?
> Pick a second `.fastq.gz` file in `data/sequences` and repeat the read count. Which of your two samples has more reads?
> {: .source}
{: .challenge}


> ## Solution
> `zgrep -c "^@" file.fastq.gz    # careful: quality lines can also contain "@" characters!`
> Counting lines that merely contain `@` can overcount, since `@` is also a valid quality-score character and may appear in the quality line by chance. Counting total lines and dividing by 4 (as in Exercise 4) is the more reliable approach for FASTQ files: a good practical lesson in why naive pattern-matching can mislead you, even when it seems to work most of the time.
> {: .source}
{: .solution}

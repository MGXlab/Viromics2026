objectives:
  - Recognise common bioinformatics file formats from their structure
  - Choose the right terminal command to inspect a given file type
keypoints:
  - The most common file formats are FASTA (nucl. and amino acid), FASTQ, SAM/BAM, VCF, GFF/GTF, BED, and plain TSV metadata tables
  - A valid FASTQ record always has 4 lines, with the sequence and quality lines the same length — mismatches signal a corrupted file
  - cat, head, tail, and less view plain-text files. zcat, zless, and zgrep do the same for gzip-compressed files
  - Match your inspection tool to the file: plain text can be opened directly, gzip-compressed text should be streamed (zcat/zless), and binary formats like BAM need a dedicated tool

It's good practice to check the contents of your data files and run regular "sanity checks" to make sure you understand what you're working with. Before we look at our own sequencing data, let's get comfortable recognising common formats and knowing how to look at them safely.

> ## Exercise 1 - Name the format
>
> Below are short, anonymised snippets. For each one, identify the file format and name one specific clue in the snippet that gave it away (a symbol, a line count, a keyword, a column pattern).
> 
> **Snippet A**
> ```text
> contig_1 length=4521
> ATGCGTACGTTAGCATGCTAGCATGCATCGATCGTAGCTAGCATCGATCG
> ```
> 
> **Snippet B**
> ```text
> @read_001
> ATGCGTACGTTAGCATGCTAGC
> +
> IIIIIIIIIIIIIIIIIIIIII
> ```
> 
> **Snippet C**
> ```text
> contig_1  Prodigal  CDS  50  409  .  +  0  ID=gene_1;product=hypothetical protein
> ```
> 
> {: .source}
{: .challenge}


> ## Solution:
> A: FASTA. Starts with `>` followed by a header, then one or more lines of raw sequence.
>
> B: FASTQ. Exactly 4 lines per record: `@` identifier, sequence, `+` separator, quality string of the same length.
>
> C: GFF/GTF. Tab-separated, 9 columns, describing a genomic feature (here a coding sequence, CDS) with a start and end coordinate.
> 
> {: .source}
{: .solution}

> ## Bonus Exercise: Spot what's broken
>
> Here is a FASTQ record someone sent you, claiming their pipeline is failing on it:
> ```text
> @read_042
> ATGCGTACGTTAGCATGCTAGCATG
> +
> IIIIIIIIIIIIIIIII
> ```
> 
> What's wrong with this record?
> Why would this cause a downstream tool (e.g. a quality-checking program) to fail or produce nonsense results?
>
> {: .source}
{: .challenge}

> ## Solution:
>
> The sequence line has 25 characters, but the quality line only has 18. They must always be the same length, since each quality character corresponds to exactly one base.
> A file with mismatched lengths like this is corrupted, and most tools will either crash outright or silently misinterpret which quality score belongs to which base. This is a good example of why a quick sanity check with `wc -l` on new data is worth doing before trusting it.
>
> {: .source}
{: .solution}

## Viewing file contents in the terminal

Terminal Basics covered navigating the filesystem and combining commands with pipes (`|`) and `>`. Video 2 introduced a few commands specifically for looking *inside* files. You'll use these constantly for the rest of the course. Let's use these to look at our sequencing data. 
Your sequencing files are gzip-compressed, so `cat/head/less` won't show anything readable if you use them directly. You need to decompress them on the fly with `zcat` instead:

```bash
zcat file.fastq.gz | head -10
zcat file.fastq.gz | tail -10
zless file.fastq.gz    # scroll with arrow keys, quit with q
```

You'll also sometimes want to search inside a file for lines matching a pattern — `grep` does this for plain text, and `zgrep` does the same for gzipped files:

```bash
grep "search_term" file.txt
zgrep "search_term" file.fastq.gz
zgrep -c "search_term" file.fastq.gz    # -c counts matching lines instead of printing them
```

> ## Exercise 4 — counting things
>
> Using `grep/zgrep`, `wc -l`, and what you know about FASTQ structure:
> 1. Count how many read identifier lines (`@...`) appear in `virome.fastq.gz`. Does it match the read count you calculated in Exercise 3?
> 2. Pick a second `.fastq.gz` file in `data/sequences` and repeat the read count. Which of your two samples has more reads?
> {: .source}
{: .challenge}


> ## Solution
> 1. `zgrep -c "@" file.fastq.gz          # careful: quality lines can also contain "@" characters!`.
> 
> Counting lines that merely contain `@` can overcount, since `@` is also a valid quality-score character and may appear in the quality line by chance. Counting total lines and dividing by 4 (as in Exercise 4) is the more reliable approach for FASTQ files: a good practical lesson in why naive pattern-matching can mislead you, even when it seems to work most of the time.
> {: .source}
{: .solution}

## Where have you actually been working?

So far today, everything you've typed (navigating folders, copying your sample data) has run on what's called the **login node**: the machine you land on when you connect to Draco. Think of it as the reception desk of the cluster: great for finding your way around, moving files, and light tasks, but it's a single machine, shared by everyone using Draco at that moment.

Any real analysis, the kind we'll do during the rest of the course, needs much more CPU and memory, often for longer periods. If everyone who uses Draco ran that directly on the login node simultaneously, it would slow to a crawl (or crash) for everyone.

Draco solves this with **compute nodes**: many other machines, dedicated to actually running the work, that you can request access to.

## The job scheduler: Slurm

You don't get to pick a compute node yourself. Instead, you describe what you need (how many CPUs, how much memory, roughly how long it'll take) to a **job scheduler** called **Slurm**, and it finds you an available compute node to run on. This keeps things fair: everyone's jobs queue up and run as resources free up, rather than everyone fighting over the same login node.

There are two ways to get access to a compute node:

- **`salloc`** — request an interactive session on a compute node, useful for quickly testing something.
- **`sbatch`** — submit a script describing the job; Slurm runs it as soon as a suitable compute node is free, without you needing to stay connected and watch it.

We'll use `sbatch` for almost everything in this course using existing scripts, so that you don't have to program much yourself.

## Anatomy of an sbatch script
Each job needs its OWN script, in which you specify what computation resources you need for the programs you w scripts are a great way to keep track of what resources you needed for the program and also what parameters your program required.

```text
#!/bin/bash
#SBATCH --tasks=1
#SBATCH --cpus-per-task=<threads>
#SBATCH --partition=<partitions,listed,here>
#SBATCH --mem=<memory>
#SBATCH --time=<hh:mm:ss>
#SBATCH --job-name=<job_name_id>
#SBATCH --output=<outdir>/<tool>.slurm.out.%j
#SBATCH --error=<outdir>/<tool>.slurm.err.%j

The actual commands you want to execute on the compute node
```

> ## Question
>
> Match each `#SBATCH` line to what it controls: number of CPUs, maximum memory, maximum runtime, which shared partitions to use, where the job's normal output goes, where its error messages go.
>
> {: .source}
{: .challenge}

> ## Solution
>
> - `--cpus-per-task` → number of CPUs (threads)
> - `--mem` → maximum memory
> - `--time` → maximum runtime — the job is killed if it exceeds this
> - `--partition` → which shared partitions to run on (we'll mostly use `short` and `standard`)
> - `--output` → standard output (normal messages / results)
> - `--error` → standard error (warnings, errors, crash messages — **check this first when something goes wrong**)

## 1. Your first job

> ## Exercise 1 — submit your first job
>
> In your home directory, create a folder `05_sbatch_practice`, and inside it, a file called `hello.sh`:
>
> ```text
> #!/bin/bash
> #SBATCH --tasks=1
> #SBATCH --cpus-per-task=1
> #SBATCH --partition=short
> #SBATCH --mem=500M
> #SBATCH --time=00:05:00
> #SBATCH --job-name=<your_choice>
> #SBATCH --output=hello.slurm.out.%j
> #SBATCH --error=hello.slurm.err.%j
>
> echo "hello from $(hostname)"
> sleep 20
> echo "done sleeping"
> ```
>
> Submit it:
>
> ```bash
> sbatch hello.sh
> ```
> {: .source}
{: .challenge}


> ## Solution
>
> You should see something like `Submitted batch job 123456`. That number is your job ID — you'll need it to check on or cancel the job.
> {: .source}
{: .solution}


> ## Discuss
>
> With a neighbour:
>
> 1. In the last lesson, was the `hostname` you saw when copying your data the login node or a compute node?
> 2. When we submit a job with `sbatch` shortly, and it prints `hostname` from inside the job, do you expect to see the same hostname, or a different one? Why?
>
> ## Solution
>
> 1. The login node — you were connected directly via Remote-SSH without asking the scheduler for anything.
> 2. A different one — Slurm will assign the job to whichever compute node is available, which will not be the login node you're typing commands into.



## 2. Watching your job run

```bash
squeue --me          # see your own jobs
squeue -u <fsuid>     # see jobs for a specific user
sstat <job_id>        # resource usage of a running job
scancel <job_id>       # cancel a job
```

> ## Exercise 2
>
> Immediately after submitting `hello.sh`, run `squeue --me` a few times in a row. What do you observe about the job's state over time?
>
> ## Solution
>
> You should see the job listed with a state like `PD` (pending) and then `R` (running), and then it disappears from the list once finished — the whole job takes about 20 seconds, so watch closely!

## 3. Reading the logs

> ## Exercise 3
>
> Once `hello.sh` has finished (it disappears from `squeue --me`):
>
> 1. Run `ls` in `05_sbatch_practice` — you should see two new files.
> 2. `cat` the `.out` file. Does its content match what you expect from the `echo` commands?
> 3. `cat` the `.err` file. Is it empty? What does an empty `.err` file usually mean?
>
> {: .source}
{: .challenge}

> ## Solution
>
> - `hello.slurm.out.<jobid>` should contain `hello from <compute node hostname>` and `done sleeping` — notice the hostname is different from the login node's, exactly as we predicted earlier.
> - `hello.slurm.err.<jobid>` should be empty, because nothing went wrong. An empty error log is a good sign, not a bug.
> {: .source}
{: .solution}


> ## Exercise 4 (optional) — diagnose a broken job
> Debugging failed jobs is one of the most useful skills for the rest of this course. If you have time, practice it now. Otherwise feel free to skip ahead to the checkpoint below.

> #SBATCH --partition=short
> #SBATCH --mem=500M
> #SBATCH --time=00:05:00

>
> NanoPlot --help
> ```
>
> This job will fail. **Without asking a TA first**, use the `.out` and `.err` files to figure out *why*.
>
> {: .source}
{: .challenge}


> ## Solution
>
> The `.err` file should show something like `CondaEnvironmentNotFoundError` — the environment `nanoplot_v9.99.9` doesn't exist (the real one is `nanoplot_v1.41.3`). This is the single most common failure mode you'll see this week: a typo in a conda environment name, a wrong file path, or a missing flag. **Always check the `.err` file first.**
> {: .source}
